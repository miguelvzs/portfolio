Do Dokploy ao Cloud Run: migrando uma plataforma de RH para o Google Cloud

Miguel Vaz · setembro de 2026

Uma plataforma de RH em produção rodava numa VPS com Dokploy, build por Nixpacks e arquivos num MinIO. Este texto conta como levei esse sistema para uma infraestrutura gerenciada no Google Cloud e as decisões que mais pesaram no caminho.

O desenho de destino

  • Cloud Run para backend (Fastify) e frontend (Next.js), na região de São Paulo. O backend de produção fica com uma instância sempre ligada; o frontend escala de zero.
  • Cloud SQL (PostgreSQL) com backup diário, recuperação point-in-time de 7 dias e proteção contra exclusão. Nenhuma rede liberada no IP público: a conexão passa pelo conector do Cloud SQL.
  • Cloud Storage no lugar do MinIO, com buckets privados. Documentos sensíveis só saem por URL assinada de 60 segundos.
  • Secret Manager com segredos separados por ambiente, e Artifact Registry para as imagens.
  • Load Balancer HTTPS com certificado gerenciado, porque o Cloud Run não oferece mapeamento de domínio nessa região.

Deploy sem chave de conta de serviço

O GitHub Actions se autentica no Google Cloud por Workload Identity Federation: o runner troca o token OIDC do próprio GitHub por uma credencial de curta duração. Nenhuma chave JSON existe para vazar. Isso deixou de ser só boa prática quando descobri que a política da organização bloqueava a criação de chaves.

O fluxo ficou assim:

  • Staging publica sozinho a cada push no branch de desenvolvimento, depois que os checks de backend e frontend passam.
  • Produção é um disparo manual que só aceita o main, consulta a API de checks e recusa commit sem CI verde, com um deploy por vez.

Por que um portão dentro do workflow? No plano gratuito do GitHub, repositório privado não tem proteção de branch. Em vez de depender disso, o próprio job verifica o estado do commit antes de publicar.

Ordem do deploy e rollback

O backend sobe primeiro e roda prisma migrate deploy no start. Se a revisão nova não fica saudável, o Cloud Run mantém o tráfego na anterior e o frontend nem é publicado. No fim, o job confere o endpoint /health. 

backend (migrate + start) → saudável? → frontend → /health
                     └─ não → tráfego continua na revisão anterior

Rollback é mandar 100% do tráfego para a revisão anterior. O runbook deixa claro o limite: se uma migration já alterou o banco, voltar só o código pode não bastar.

Restrições que mudaram o plano

  • Chave de conta de serviço bloqueada: além do Workload Identity no CI, troquei o acesso a arquivos via API S3 (que exigiria chave HMAC) pelo cliente nativo do Cloud Storage.
  • Acesso público bloqueado: o serviço foi exposto com a verificação de invoker desligada e protegido pela própria aplicação.
  • Build no Cloud Build pedia criar bucket: as imagens passaram a ser construídas no runner e enviadas ao Artifact Registry.
  • Nome de bucket é único no mundo: um prefixo configurável mapeia o nome lógico para o real, e as URLs de mídia já gravadas no banco não precisaram mudar.
  • Proxy na frente: configurei os ranges do Google como proxy confiável para o rate limit enxergar o IP real de quem acessa.

Virada em fases

A migração entrou em etapas: primeiro a preparação (imagens e storage prontos, com a infraestrutura antiga ainda no ar), depois a virada e, por fim, a remoção do deploy antigo. O banco veio de um dump com políticas de RLS herdadas, que exigiram recriar papéis antes do restore.

Um detalhe que só aparece em produção: durante a troca de revisão, as duas versões rodam juntas por alguns segundos e jobs agendados executam em dobro. Como as gravações usam ON CONFLICT, a duplicação é inofensiva.

Observabilidade e custo

  • Uptime checks a cada 5 minutos na API e no site, com alerta quando a falha aparece em mais de uma região.
  • Alerta de orçamento em 50%, 90% e 100% e sobre a previsão do mês. Ele avisa, mas não desliga nada.
  • Custo estimado por ambiente, com o staging dimensionado para escalar até zero.

O que eu levaria para a próxima migração

  • Descobrir as políticas da organização antes de desenhar a solução. Três delas mudaram o plano.
  • Tratar migration de banco como parte do rollback, não como detalhe.
  • Colocar o portão de qualidade no próprio pipeline, em vez de depender da configuração do repositório.
  • Escrever o runbook durante a migração. Ele virou a documentação de operação.
